Start

Install Forge

Prerequisites

  • Python 3.12 or newer
  • uv for dependency management
  • Git, plus ripgrep for fast workspace search
  • A provider API key, or a local runtime such as Ollama, LM Studio, or vLLM

Clone, sync, and run

$ git clone https://github.com/Chenboda01/Forge-AI.git $ cd Forge-AI $ uv sync --extra dev $ uv run forge doctor $ uv run forge chat

Credentials

Forge reads credentials from the live process environment first, then the operating-system keyring.

$ export DEEPSEEK_API_KEY="sk-..." $ uv run forge auth login deepseek $ uv run forge auth list $ uv run forge provider test deepseek

Forge does not read project .env files. If secure storage is unavailable, it fails closed instead of writing a plaintext fallback.

Choose a mode

$ uv run forge chat # ASK (default): read-only $ uv run forge chat --mode architect $ uv run forge chat --mode build # mutations still require approval

Inspect the catalog

$ uv run forge models $ uv run forge providers

Runtime

How Forge works

Forge is workflow-first. The model recommends actions; the runtime controls permissions, approvals, limits, patches, validation, and recovery.

1

Understand

Parse the task, constraints, and workspace before touching anything.

2

Inspect

Search and read only the relevant files, then check Git state and project instructions.

3

Plan

Choose the smallest complete change and the validation evidence it needs.

4

Approve

Writes, patches, commands, and deletions wait for a trusted, explicit approval.

5

Apply

Match the exact preview, checkpoint first, serialize writers, and roll back on failure.

6

Validate

Run restricted commands, review the diff, and report evidence — never an unsupported claim.

State

Save a session, restore a checkpoint

Sessions and checkpoints are different things. A session is your conversation. A checkpoint is the exact pre-patch content of the files Forge is about to edit.

Save and resume a session

  1. Work normally until the conversation is worth keeping.
  2. Run /save release-prep. The optional name appears in /sessions.
  3. Forge redacts secrets and writes .forge/sessions/<id>.json atomically.
  4. Run /sessions to list IDs, then /resume ID to restore the conversation and token counts.

/new saves the current conversation automatically before clearing it. Nothing is saved on exit, so run /save first.

Inspect and restore a checkpoint

  1. Every applied patch creates a checkpoint before writing to disk.
  2. Run /checkpoints to list every ID, time, task, patch, and file count.
  3. Run /undo ID to restore those files. /undo alone restores the latest checkpoint.
  4. Records live in .forge/checkpoints/<id>.json and are validated before restore.

Checkpoints cover only the files a patch touched. New files are removed on undo; edited files get their original content back.

Trust

Security by design

  • Keyring-first credentials. Forge does not read project .env files and fails closed rather than falling back to plaintext storage.
  • No silent provider fallback. A failed request is reported; Forge never changes provider or privacy boundary behind your back.
  • Workspace containment. Traversal and external symlinks are rejected. Restricted secret files and private .forge state are denied to model-facing tools.
  • Prompt-injection defense. Repository content, comments, and tool output are untrusted data. They cannot grant permissions or override policy.
  • Approval gating. Writes, patches, commands, and deletions require a trusted one-shot approval. A model cannot approve its own action.
  • Restricted command execution. Argument arrays only, a secret-free environment, a Linux user/network namespace, timeouts, process-group termination, and bounded output.
  • Redaction by default. Configured secrets are redacted before terminal rendering, validation records, and persisted sessions.
  • Pinned updates. Updates require explicit approval and install an exact binary package version; Forge does not execute mutable Git sources.

Status

Current state and next

Forge is a pre-release prototype. The workflow core, patch pipeline, validation boundary, sessions, recovery, subagents, and terminal interface are implemented and covered by executable tests.

Remaining work includes:

  • Tester and Coder subagents, plus structured subagent reports.
  • A structured event bus with per-tool subagent activity.
  • Slash, path, model, and mention autocomplete.
  • A benchmark suite that measures self-improvement.
  • A cross-platform test matrix and evidence-backed support statement.
  • Clean-environment packaging and release artifacts.
